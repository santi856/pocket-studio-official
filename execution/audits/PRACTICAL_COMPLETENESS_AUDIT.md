# Practical Product Completeness Audit — Pre-Phase-3 Forensic Audit (Part 5)

## Pipeline layer-by-layer

**Product idea → Product Intelligence**: real (mock-provider-backed) intent/category extraction. `src/lib/orchestration/product-intelligence.ts`. Inferred, not tested against ground truth (no "did the AI understand this correctly" evaluation exists — there is nothing to evaluate against, since it's deterministic keyword matching, not a model).

**→ implied requirements**: `requirements-engine.ts` `deriveRequirements`. One requirement per detected Impact Analysis category, `basis: "inferred"` always (no "explicit" tracking exists at this layer — only the interaction-contract layer, below, has an explicit/inferred axis). Implemented and tested (`requirements-engine.test.ts`).

**→ recognized product patterns**: `interaction-contracts.ts` `inferScreenPatterns`/`inferWorkflowPatterns`. **Closed set of 5 patterns**: `list-view`, `detail-view`, `form-submission`, `multi-step-workflow`, `destructive-action`. Implemented, tested, deterministic.

**→ interaction contracts**: same file, `mergeContract`. Before this session's repair: computed, stored, structurally checkable — but the checker was optional, workflow contracts were dead data, and 2 of 7 states had no renderer implementation. After the repair: required validation (screens + workflows), 6-value classification (required/conventionally_implied/recommended/optional/consequential_decision/unresolved), a real explicit/inferred `stateBasis` axis, and a real `unsupportedStates` capability-gap list. **This was the single largest gap in the whole pipeline and is now closed** — verified by 18+ new unit tests plus integration tests proving the mechanism end to end.

**→ Blueprint**: `blueprint-generator.ts`. Deterministic, grounded in Product State/DNA/Requirements — no field invented. Real (`blueprint.integration.test.ts` and friends).

**→ Build Plan**: `build-planner.ts`. Was consuming _screen_ contracts for its `tests` facet but silently ignoring _workflow_ contracts entirely (a workflow got one generic test string regardless of its real required states). Fixed in this session's repair — `deriveTests` now derives real per-state test strings for workflows too.

**→ Component Registry**: closed 29-primitive set, real Zod validation, fail-safe on unknown types. No per-component _behavioral_ capability declaration exists (e.g. nothing formally declares "a Button supports a disabled prop") — the registry is a shape/type contract, not a behavior contract. This gap is only partially closed: the _renderer_ now really implements `disabled-while-pending` on submit buttons (via `useFormStatus`), but the Component Registry's own schema still doesn't formally require or declare it.

**→ generated implementation**: `component-renderer.tsx`. Real interactive DOM. As of this session: real Retry (ErrorState → `router.refresh()`) and real disabled-while-pending (submit Button → `useFormStatus`). Both independently verified: reverted, confirmed a test fails without the fix, restored, confirmed it passes — the same adversarial-self-verification discipline used throughout this project.

**→ renderer/runtime**: covered above. One capability confirmed genuinely absent: `List` items have no click/keyboard interactivity at all — but this is not a violated _requirement_, because "selectable list item" is not a state in the current 7-state vocabulary. This is a real scope boundary of the vocabulary itself, worth naming as a candidate for a future pattern (`list-view` → `navigable-list-item`) rather than an unmet requirement.

**→ generated or workflow-derived tests**: `deriveTests`. Produces human-readable description strings ("Home: verify the 'loading' state."), not executable test code. **This is declarative, not enforced** — nothing runs these as real assertions against the generated app. The Quality Gate is the actual enforcement layer; the `tests` array is documentation of intent.

**→ Quality Gate**: `quality-gate.ts`. Was 8 checks, now 11: structural validity, Build Plan readiness, interaction-contract completeness (screens+workflows), **unsupported-state detection**, **consequential/unresolved disclosure verification**, **unwired-Button detection**, list-view data-binding, form-field matching, screen reachability, alt-text, server-side data-binding smoke test. All 3 new checks were verified via genuine database-corruption negative tests (inject a bad value into a real stored Blueprint/Build Plan row, confirm the check fails, confirm `result.passed === false`) — not merely unit-tested against synthetic in-memory data.

**→ Evidence Ledger / Truth Status**: real writes on every Quality Gate run. Truth Status granularity was one flat rollup (`quality.gate`); now also 5 real per-dimension keys (structural/behavioral/accessibility/governance/operational), independently verified to diverge correctly (a missing alt tag blocks only `quality.accessibility`).

## Can Pocket Studio still generate something hollow?

**Yes, and the exact path is now narrower but not eliminated:**

1. **Content shallowness, not behavioral hollowness.** The single largest remaining gap is that `blueprint-templates.ts`'s category→screen/data-model map is small and generic (confirmed: the official §56 demonstration idea produces only Home/Browse with zero data models). A customer describing a rich domain (barbers, availability, memberships) gets a real, non-decorative, fully wired _shell_ — but its content is far shallower than their idea implied. This is **truthful but thin**, not **hollow but decorative**: every screen that does get generated has real loading/empty/error states, real data binding, and passes the Quality Gate. The gap is coverage, not honesty.
2. **Unmodeled pattern families** (search/filter, pricing/plan selection, real generated-app authentication) get no interaction-contract-specific behavior at all — they silently fall back to the nearest generic pattern. A generated "search" screen would look and behave exactly like a plain list-view, with no query-specific empty/loading distinction. This is a real, honest gap (not claimed as covered anywhere) but it means a customer asking for search functionality gets something visually plausible that does not actually implement search-specific UX.
3. **`List` items are not clickable/selectable at all**, and no interaction-contract state currently requires them to be — a generated "Browse barbers" list is real (real data, real empty/error states) but a customer cannot click a barber to see their profile from that list; only the fixed navigation graph's own links work.
4. **Durable jobs are scaffolded but never wired** — if Phase 3 UI work ever exposes `runGenerationJob` to a real route without re-auditing it, the customer-visible behavior would depend entirely on code that has real tests but zero live callers today (confirmed by grep).

None of these represent "polished but unusable" — every screen this session actually generated and rendered (via the demonstration product and the barber-scenario trace) is genuinely usable within its narrow scope. The honest characterization is **real-but-shallow**, not **fake-but-impressive**.
