3. **Decision Ledger naming collision**: `execution/decisions/ledger.jsonl` (a build-process artifact, D-0001..D-0041) and the product-facing `Decision` Prisma model (Master Spec §15, a _customer-facing_ approve/decline mechanism) share the word "Decision Ledger" but are different systems serving different purposes. ## Part 11 — Overbuilding, underbuilding, and architectural risk

**Systems too shallow relative to their name/promise**: "Product Knowledge Relationships" (§12) — populates nodes (SCREEN/WORKFLOW/DATA_MODEL/ACTION) but no edges were observed being created in the generation path read this session; "relationships" is aspirational relative to what's actually persisted. **Durable jobs** (§29) — fully real and tested, but zero live callers; a complete, race-safe, evidenced system with no customer-reachable path to it yet, which is a strange kind of overbuilding-relative-to-current-use (not wasted effort — it's the right foundation — but currently inert).

**Duplicated sources of truth, found and assessed**: the `quality.gate` flat rollup + 5 new per-dimension keys (Part 7) — deliberate, additive, low risk (same source computation, no drift possible without a coincident bug in the dimension-mapping table itself). Not a finding requiring repair.

**Registries whose enforcement lagged their declaration**: the Capability Registry's 3 stale entries (Part 4/12) are the clearest instance in this codebase of "a schema/registry that creates the appearance of accurate capability tracking without a process that keeps it current." No automated mechanism ties a Capability Registry entry's `implementationLevel` to actual shipped code — it is entirely dependent on a human (or an agent acting as one) remembering to update it. **Recommend, as a non-blocking Phase 3 hygiene item**: some form of periodic reconciliation check (even a simple, hand-run audit like this one) rather than assuming registry accuracy persists automatically.

**Tests that prove structure rather than outcomes**: not found as a systemic pattern — the tests read this session (Quality Gate's new checks especially) consistently assert on real, corrupted-database-driven outcomes rather than mocked internals. The one partial exception: `deriveTests`' generated test-description strings (Part 5) are themselves declarative, not executable — a real, disclosed limitation, not a hidden one.

**Generic placeholders / hardcoded demonstration behavior**: explicitly and repeatedly _avoided_ by design (D-0028's own reasoning against hardcoding the official demonstration sentence is a genuine, principled decision, independently confirmed still in effect by this session's barber-scenario trace showing the identical generic behavior for a _different_ idea — proving the system really is idea-agnostic, not secretly special-cased).

**Coupling that will make Phase 3 expensive**: the Interaction Contract System is now load-bearing across Blueprint validation, Build Planner, the renderer, and the Quality Gate (5 real consumers as of this session's repair). This is _appropriate_ coupling (a single source of truth consumed correctly in multiple places, the opposite of the "declared but unconsumed" state it was in before this session) but it does mean any future change to the state vocabulary (e.g. adding a "selectable list item" state, named as a real gap in Part 4/5) now has to propagate correctly through all 5 consumers, verified by tests each time — a real, now-larger surface area to keep synchronized, which is the direct, honest cost of having closed the "declared but not implemented" gap this session targeted.

**Missing boundaries Phase 3 could worsen**: prompt-injection/generated-code trust boundaries (Part 6) — currently dormant because there is no live AI provider; Phase 3's own stated scope is exactly "connect a live AI provider," which will make this a live boundary on day one of that work, with zero existing mitigation code to build on.

**Architecture that should be preserved as-is**: the tenant-isolation choke point (`authz.ts`), the append-only versioning discipline (`createNextVersion`, applied consistently across 8+ models), and the "never silently invent a consequential decision" discipline (verified independently at three separate layers — Blueprint openDecisions, Build Planner blockers, full-orchestration status) are all genuinely sound, consistently applied, and should not be touched by Phase 3 work except to extend the same patterns to new systems.

**Architecture that must be repaired before Phase 3, named precisely**: (1) the test-suite scheduling/isolation fragility found in Part 7-8 — real, reproducible, environmental-but-unresolved; (2) the Capability Registry's lack of any automated freshness check — process risk, not urgent, but compounds every future phase; (3) credential key rotation — absent, directly relevant to Phase 3's "real credentials" scope.
