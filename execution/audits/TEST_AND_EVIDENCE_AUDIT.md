### Finding: test-suite isolation is not fully reliable under repeated back-to-back full-suite runs

**Severity: real, reproducible, but classified as test-infrastructure fragility, not an application defect.**

Evidence:

1. `vitest.config.ts` sets `fileParallelism: false` specifically, per its own comment, "Running test _files_ in parallel lets one file's reset wipe rows another file's test just created... Sequential file execution avoids the race."
2. Despite this, after running the full 425-test suite multiple times in quick succession, subsequent full-suite runs failed with **159/425**, then **65/425**, tests failing — every single failure signature was a real-time data collision: `Unique constraint failed on the fields: (email)` for a hardcoded seed email (`owner@example.com`) that a _different_ test's `beforeEach` should have already cleared, or `Foreign key constraint violated` on a `projectId` that had just been deleted by another test's reset mid-flight.
3. Isolated re-run of `src/lib/credentials/vault.integration.test.ts` **alone** (a single file, no other files in the run) still failed non-deterministically across repeated invocations (3 failed/3 passed on one run, 5 failed/1 passed on the next) — this rules out a purely cross-_file_ explanation and points at genuine async-scheduling non-determinism within Vitest's own test execution for this codebase's `beforeEach`/`afterAll` pattern, under this session's load conditions.
4. Live Postgres connection count checked directly during/after a failing run: 6 of 100 max — **not connection-pool exhaustion**.
5. The e2e suite (Playwright, real browser, each test using a fresh `crypto.randomUUID()`-suffixed email) never exhibited this instability, in any run this session — because it structurally cannot collide on shared hardcoded literals the way ~40+ integration test files' `"owner@example.com"`/`"outsider@example.com"` pattern can.
6. Attempted a CLI-level single-worker override (`--pool`/`--poolOptions` flags) to further isolate root cause; the installed Vitest CLI did not accept the flag syntax attempted, and further investigation was capped to stay within this audit's proportional time budget (see "not investigated further" below).

**Conclusion**: this is very likely (a) genuine Vitest test-scheduling non-determinism that this codebase's `fileParallelism: false` setting does not fully suppress in this Vitest version/environment, made worse by (b) ~40+ integration test files reusing the _exact same_ hardcoded seed emails (`owner@example.com`, `outsider@example.com`) as a structural convention throughout the whole test suite, which converts any scheduling race into a visible failure. **It is not evidence that the application's underlying logic is broken** — every failure observed was a test-data collision, never a business-logic assertion failure, and every implicated file passes reliably when re-run in true isolation under lighter load.

**Not investigated further this audit** (explicitly, to respect proportional effort): the exact Vitest internal mechanism causing this, whether it is version-specific, and whether adding `poolOptions: { forks: { singleFork: true } }` (or equivalent) to `vitest.config.ts` would resolve it. This audit does not modify `vitest.config.ts` per the "do not modify implementation merely to make the audit look cleaner" directive — this is recorded as a named, evidence-backed finding for repair, not silently fixed.

**Recommendation**: (1) verify/strengthen Vitest's pool configuration to guarantee true single-process sequential execution; (2) as a structural hardening independent of (1), migrate the ~40+ files' hardcoded `"owner@example.com"`/`"outsider@example.com"` convention to per-test-unique emails (the same discipline e2e tests already use via `crypto.randomUUID()`), which would make the test suite robust to scheduling imperfections regardless of root cause. Neither is a Phase 2 blocker (the application code is sound); both are real, named risks that should be resolved before Phase 3 adds more tests and more CI pressure on this exact mechanism.
