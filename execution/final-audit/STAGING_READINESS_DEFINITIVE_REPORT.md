# Pocket Studio — Staging-Readiness Definitive Report

Date: 2026-07-26. Commit range audited: through this report's own commit. Produced by tracing real runtime paths (file-by-file, call-site-by-call-site) — not inferred from names, comments, tests, or schemas alone. Two research sweeps (mechanical grep-based fact-finding: TODOs, dead code, unused models, feature flags, env vars, admin surfaces, mobile/export/legal/observability reality) were independently verified before being incorporated; every claim below cites its own evidence.

---

## 1. EXECUTIVE VERDICT

**LOCAL ONLY.** The core builder journey (signup → org/project → conversational generation → live preview → consequence-aware editing → persistence → generated-app customer auth → account deletion) is real, working, and verified — repeatedly, across this and prior sessions, by both automated tests and live browser automation. But three things block even a private pilot: **(1) there is no way for a real customer to ever start a paid subscription** (no Stripe Checkout session creation exists anywhere in the codebase — confirmed in code, not inferred), **(2) there is no cap of any kind on AI generation cost or frequency** (a single customer, or an unauthenticated abuser once account-creation is unthrottled, could generate unbounded real API cost the moment a real Anthropic key is configured), and **(3) no staging or production environment exists** — everything verified so far has only ever run on a local dev machine. None of these are visible from a passing test suite; all three were found by tracing runtime behavior directly.

## 9. LOGIC FLAWS FOUND

1. **No real checkout path exists**, so the entire billing _state machine_ (real, well-built, webhook-verified) has no real customer-facing entry point. This is not visible from any test — every billing test seeds a subscription directly.
2. **`GeneratedAppUser.role` is inert.** A Blueprint can define "customer" vs. "owner" roles, but nothing in the runtime ever checks which role the authenticated user has — every generated-app customer has identical effective permissions regardless of their stored role.
3. **`resolveIntent` (the first AI call on every single idea/edit submission) had no error handling of any kind** before this pass — a real Anthropic timeout or malformed response would propagate uncaught to Next.js's bare default error page, discarding the customer's typed input. Fixed in this pass (§14) — but this shape of gap (a real external-call failure with no catch) should be checked for at every other live-provider call site as a standing practice, not assumed closed everywhere just because this one instance was found and fixed.
4. **No error boundary of any kind existed anywhere in the app** before this pass (`error.tsx`/`global-error.tsx`) — any uncaught exception in any Server Component or Action, not just the one above, hit Next.js's raw error page. Fixed in this pass.

## 10. SECURITY RISKS FOUND

This is a **code audit and automated-test result**, not a penetration test or production verification — no staging/production environment exists yet to verify against.

- **No security headers configured anywhere** (no CSP, X-Frame-Options, HSTS, etc.) before this pass — confirmed by reading `next.config.ts` in full and confirming no `middleware.ts` exists. Baseline headers added this pass (X-Content-Type-Options, X-Frame-Options, Referrer-Policy, Permissions-Policy). **No CSP was added** — a correct one requires its own dedicated review given generated screens render customer-influenced content, and shipping an untested CSP would be worse than disclosing its absence.
- **No rate limiting beyond login** — signup and AI generation are both unthrottled. Combined with finding above (no AI cost cap), this is a real, compounding risk once real AI credentials are configured.
- **Secrets**: real AES-256-GCM encryption, fresh IV per call, key from environment — this specific mechanism is sound. Repo-wide scan for committed secrets: none found.
- **CSRF**: Next.js Server Actions verify the request's `Origin` header against the deployment's own origin by default (a framework-level guarantee, not this codebase's own code) — not independently re-verified against a real deployed origin in this pass, since none exists yet.
- **XSS**: only two `dangerouslySetInnerHTML` call sites in the whole app, both the same already-reviewed, disclosed service-worker registration snippet (static, developer-authored content, not customer input).
- **SQL injection**: all database access goes through Prisma's parameterized query builder; no raw `$queryRaw`/`$executeRaw` calls exist anywhere in `src/lib` (grepped directly).
- **Dependency vulnerabilities**: `npm audit` found 8 known vulnerabilities (4 moderate, 4 high) in transitive dependencies. One (valibot) was fixed this pass via `npm audit fix` (verified: full 808-test suite and typecheck still pass after). The remaining 7 (postcss/sharp, bundled inside `next`'s own dependency tree) require either `npm audit fix --force` (installs `next@16.2.12`, outside this project's currently declared version range) or waiting for an in-range patch — **not applied in this pass**, disclosed rather than forced through without dedicated regression-testing time for a framework version change.
- **Brute-force protection**: real, tested, advisory-lock-based rate limiting on login only (`src/lib/auth/login-rate-limit.ts`).
- **IDOR**: every tenant-scoped function is mechanically checked by `src/lib/tenancy/verify-tenant-isolation.ts` (a real static analyzer, not just a convention) — re-verified clean this session after two new features were added.

## 11. DATA-ISOLATION FINDINGS

- **Pocket Studio platform (org-to-org)**: real, tested, both at the service layer (every mutation requires `requireOrganizationMembership`/`requireProjectAccess`) and at the browser level (`e2e/tenant-isolation.spec.ts` — a forged `organizationSlug` in a real request fails gracefully, creates nothing cross-tenant; passing).
- **Generated-app-to-generated-app**: real. `requireGeneratedAppSessionForProject` (this session's own addition) verifies a session's owner belongs to the _exact_ project requested — a session minted for one generated app is rejected by a different one, tested directly (`generated-app-session.integration.test.ts`).
- **Generated-app customer-to-customer, within the same app**: real. Every `GeneratedRecord` read/write is scoped to `ownerGeneratedAppUserId`, verified this session (a second customer's submission is invisible to the first).
- **Static enforcement**: `verify-tenant-isolation.ts` scans every exported, tenant-scoped function in `src/lib` on every test run — zero violations, mechanically guaranteed, not just currently true by inspection.

## 12. AI COST AND ABUSE FINDINGS

- Provider: Anthropic (`claude-sonnet-5`), mock by default, real only when `AI_PROVIDER=anthropic` + a real key is set.
- Calls per generation: at minimum one (`resolveIntent`) for every idea/edit submission; a second (`extractProductSemantics`) for the deeper semantic-compiler path, itself retrying up to twice before falling back.
- Token limits: `max_tokens` is bounded per call (1024 for intent resolution, 8192 for semantic extraction) — bounds the size of a _single_ response, not the number of calls.
- Retry limits: 2 attempts for semantic extraction; **0** (none) for intent resolution before this pass's fix (which adds graceful failure, not a retry).
- **Maximum concurrent generations: none enforced.** **Project limits: yes** (plan-based, `entitlements.ts`). **Rate limits on generation: none.** **Monthly usage limits: none.** **Spending caps: none.**
- **Can one customer create unbounded AI cost? Yes**, confirmed directly — nothing between a customer's submit click and a real, billed Anthropic API call checks any prior usage, cost, or frequency.
- **Can a nonpaying user consume paid AI resources? Yes** — the only entitlement enforced is a project _count_ limit; a customer on the free `FREE_EXPLORE` plan can submit unlimited idea/edit requests against however many projects that plan allows, each a real, costed AI call once credentials are configured.

## 13. BILLING ENFORCEMENT FINDINGS

Traced directly, not assumed:

- **Free user**: default `FREE_EXPLORE` plan entitlements apply (project-limit + export-allowed only) — real.
- **Trial/paid user**: the billing _state machine_ (`src/lib/billing/access.ts`) correctly transitions and enforces plan entitlements once a subscription exists — real, tested. **But no real customer can ever reach this state through the product's own UI** — no checkout flow exists to create a `billingProviderCustomerId` in the first place.
- **Failed payment / grace period / restriction**: real, tested state transitions (webhook-driven) — reachable only via a directly-seeded or webhook-simulated subscription in tests, never via a live customer flow yet.
- **Cancelled/expired subscription**: real; customer-owned data is correctly, verifiably preserved through the entire lifecycle (Master Spec §62, tested end to end in `customer-data-protection.integration.test.ts`).
- **Duplicate/delayed webhook**: real idempotency handling exists (`ProcessedWebhookEvent` dedup table) — tested.
- **Refunded payment**: no distinct handling found beyond the general billing-event state machine; not separately tested.
- **Account deletion**: real, separate from the billing lifecycle by design (this session's own feature) — genuinely deletes Project/GeneratedRecord/etc. after a 30-day grace period, correctly preserves billing/invoice history.

## PHASE 3 — STAGING DEPLOYMENT RECOMMENDATION

**Recommended: Vercel**, not Coolify/VPS, for staging specifically.

Reasoning against the actual repository architecture: Next.js App Router with no WebSocket/streaming requirement found anywhere, no background job queue in real use (a `JobRun` durability model exists for generation but runs synchronously within a request, not via a separate worker), no filesystem-persisted artifacts (exports stream JSON directly from the database, mobile "project files" are held in memory/DB, never written to a local disk path the server would need to retain across requests), and a standard Prisma+Postgres connection reachable over the network (already using `@prisma/adapter-pg`, not a local-socket-only setup). This is close to the textbook case Vercel's serverless model is built for. Coolify remains the right call for Vortecx Labs' eventual multi-project, more customized, cost-sensitive production platform (see `docs/vortecx-ai-operations/`) — but that is a different question from "fastest, lowest-maintenance path to a working staging URL right now," which Vercel wins on for this specific need.

- **Exact recommended plan**: Vercel Pro (~$20/month per member). The Hobby tier's default serverless function timeout (10s) is very likely too short once real AI-backed generation is enabled — this app's own Anthropic client has a 30s request timeout, and generation can involve two sequential calls. Pro's longer function-duration limits are a real requirement here, not a nice-to-have.
- **Database**: a real, network-reachable Postgres is required (Vercel's serverless functions cannot reach a local Docker Postgres). Recommend **Neon** (Vercel's native Postgres integration, generous free tier sufficient for staging-scale traffic, zero additional account-management overhead beyond what connecting the integration requires).
- **Expected monthly cost**: ~$20 (Vercel Pro) + $0 (Neon free tier at staging scale) = **~$20/month** to start.
- **Exact account to create**: a Vercel account (GitHub-connected, so deploys trigger from this same repository), and a Neon database provisioned through Vercel's own integration marketplace (no separate signup needed).
- **Exact information the founder must provide**: authorize the Vercel GitHub App against this repository (least-privilege, repo-scoped — not a personal access token), and the real values for `SESSION_SECRET`/`CREDENTIAL_ENCRYPTION_KEY` (freshly generated for this environment, never reused from local dev) entered directly into Vercel's environment-variable UI — never into this repository or into chat.
- **Exact next action once the founder responds**: connect the repository in Vercel, set the environment variables listed in `docs/DEPLOYMENT.md`, trigger the first deploy from `main`, then run this same repository's e2e suite against the real deployed URL (Phase 5) rather than local dev — the actual verification this report cannot yet provide.
